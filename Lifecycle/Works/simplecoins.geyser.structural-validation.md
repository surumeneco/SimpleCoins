## Source-grounded acceptance and boundaries

- **Design provenance**: Approved 1.0.0 behaviour preserves nine stable denominations, fixed `item_model` and PDC monetary identity across JE/BE. Without Nexo, SimpleCoins generates its own Geyser v2 custom mapping and resource pack. The generation is not proof of client delivery.
- **Observed defect in current `develop`**: `GeyserResourceInstaller.validateMapping` checks only substring presence of `format_version` and the nine `bedrock_identifier` strings. This accepts invalid, truncated or malformed JSON and wrong `model`/`icon` associations if the identifiers appear somewhere else; it can stage unusable custom-content data while claiming a valid preflight. UTF-8 decoding replaces malformed bytes rather than rejecting them.
- **Technical scope**: validate the **exact canonical Geyser JSON v2 document generated by `BedrockPack.write`**, including all nine ordered denomination definitions (`model`, `bedrock_identifier`, `icon`, type, max stack 64) and syntactically well-formed JSON string display names. Reject trailing bytes, duplicate or omitted entries and malformed UTF-8 *before* `ManagedResources` mutates provider content. This is a strict producer-consumer contract, not a change to user-selected display names or to Nexo delegation.
- **Tests**: materialize the source map using the generator; mutate one model field, append additional JSON or invalid UTF-8 bytes; confirm that staging fails and leaves the managed provider absent/unmodified. Existing positive staging, integrity and Nexo ownership regressions must still pass. This is a finite source-bounded change with no player admission effect.
- **Out of scope**: Geyser runtime-side JSON acceptance, Bedrock client receipt, Java pack HTTP service, Nexo/Scaffolding, editing provider config, or actual monetary issuance. Keep `main` untouched and the independent admission guard default-deny.
- **CAT**: project normative Process/PI/TCE semantic confirmation and formal Gates remain `not-run`; a generated Work Draft, JUnit Red/Green or CI success is not normative CAT conformance.
